# 消息表情回应（msg-reaction）

让机器人像真人一样贴「表情回应」——就是 QQ 里长按消息时顶上那排 👍 😳 🍰 😨 😴 😂。

它做两件事，走**两条互不干扰的路**：

| 路径 | 什么情况 | 谁决定 | 限频 |
|---|---|---|---|
| **自动** | 机器人自己发了消息 | 先掷**概率**，过了再让 AI 按这句话的语气挑 0~N 个 | 概率 / 冷却 / 小时 / 每日，四重闸门全部可调 |
| **按需** | 群里**有人明说**「给我贴个赞 / 回个表情」 | 模型决定贴哪个 | 不受上面四个闸门约束，只留 5 秒防连点 |

两条路的**计数与配额完全隔离**：按需贴一次，不会消耗概率、不刷新冷却、不占小时/每日额度。
否则"我点了一次名，接下来五分钟它就不按我的设置了"。

## v1.3：模型不能再擅自贴了（「必须明说才贴」）

v1.2 加了工具，但实测出现新问题：**模型因为"被 @"就顺手贴**，于是看起来又变回"百分百贴"。

工具描述和提示词里怎么叮嘱都不够可靠 —— 所以 v1.3 做成**代码级拦截**：
模型调用 `贴表情回应` 时，插件会先检查这个群最近 3 条别人发的话里有没有"要表情"的意思，
没有就直接把这次调用**拦下来**（`isError` + 一句解释），一个都贴不出去。

判定规则（`isReactionRequest`，刻意保守，宁可拦错也不放宽）：

| 命中即算"要求了" | 例子 |
|---|---|
| 出现对象词 `表情 / 赞 / 比心 / 回应 / 反应 / emoji` | 「给我贴个赞」「反应一下」 |
| 给动词 + 表情字符 | 「给我个 👍」 |
| `贴 / 加 / 补` + 量词 | 「贴一下」「加个」 |
| 短句里含「贴」 | 「贴一个」 |

单纯 **@ 一下、夸一句、日常聊天一律不算**（「你真厉害」「回一下消息」都会被判为没要求）。
故意不拿「喜欢 / 同意 / 难受」这种含义词去匹配 —— 它们是日常用词，会误判。

想放开这道闸的最小值开关在设置里：**「只有别人明说要贴时才允许模型贴」**（默认开）。
关掉之后模型可以自己判断，但那会绕开概率与所有上限，表情会明显变多。

## v1.4：数值真的按你填的生效（修了两个"数字失真"的洞）

**用户反馈**：「把概率调到百分百的时候怎么没有效果，我要求这些框填的数字与概率都是真实有效的。」

排查出两个真问题，都会让设置里的数字对不上实际表现：

### 洞 ①：概率被掷了两次 → 填 20% 实际是 36%

热重载用 `?t=时间戳` 重新 import 插件，每次都是**新的模块实例**。
原来只靠 `proto.call.__msgReaction` 认领补丁，实测不够 —— 日志里**每条发送都打了两行**观测记录，
打印调用栈能看到**两代不同实例的补丁同时在链上**，补丁被套了两层。

一次发送走两次判频，概率就掷了两遍：`1-(1-0.2)² = 36%`。填 100% 看不出差别，
但填 20%/35% 之类的，实际频率明显高于设定值。

修法两层：
- `installSendHook()` 改成**先剥洋葱再包一层**：沿 `__msgReactionOriginal` 一路退到"真身"，
  保证原型链上的补丁层数**恒等于 1**（不管被热重载多少次、核心模块有没有被重新加载过）。
- `onOutboundSent()` 按 `会话#消息id` 去重（10 分钟窗）：就算补丁真的叠加了，
  同一次发送也只决策一次。

自检里加了 ㉚（设 50% 抽样 3000 次实测 50.2%）钉住它。

### 洞 ②：目标是「被回复的消息」时，可能永远找不到目标

机器人不是每句话都会引用别人。`replyTargetOf()` 取不到 id 时，原代码直接静默返回 ——
**概率调到 100% 也一条都贴不出来**，看起来就是"设置没用"。

修法：新增设置 **`fallbackToSelf`**（默认开）—— 找不到目标就退回贴它自己刚发的那条。
关掉则维持原来的"什么都不贴"。自检 ㉙ 正反两面都压了。

### 洞 ③（这才是最要命的）：每日上限被悄悄打满，之后一整天都"没效果"

查 `data/msg-reaction/state.json` 时看到的：

```
group:1102382705  dayKey=2026-10-11  dayCount = 15 / 15   ← 已经满了
```

`maxPerDay` 默认 **15 次/会话/天**。当天早些时候自动贴已经把它用光了，
于是**从那一刻起到当天 24:00，无论概率调成多少都一条都贴不出来** ——
这正是"概率调到 100% 没效果"的直接原因。

更要命的是：这种情况**日志里什么都不打**（只是静默跳过了），
所以从外面完全看不出是"概率没生效"还是"被上限卡住了"。

处理方式见下一条：把"为什么没贴"摊开，并且额度满时直接在面板上提示。
另外要立刻见效的话，**重启一下机器人**（计数器在内存里，跨重启由 state.json 累计，
自然跨天也会自动归零）。

### 顺带：把"为什么没贴"摊开

状态面板新增一行**「跳过原因」**，直接列出是被哪个闸门拦的，例如：

```
跳过原因   会话冷却中 8 · 随机跳过 42 · 已达每日上限 3
```

新增设置 **`logSkips`**（默认关）：打开后每次决策都写一行日志，含结果。
之前只有一个「跳过 N 次」，光看数字分不清是概率没过还是被冷却拦了。

## v1.2：补上「按你要求去贴」这条口子

v1.1 之前**只有自动路径**。群友说「给我贴个赞」时，模型手里根本没有这个工具，
只能回一句「**贴不了**」——看起来就像插件坏了（真实反馈就是这样来的）。

v1.2 加了工具 **`msg-reaction__react`（贴表情回应）**：

- **默认贴到"本会话最近一条别人发的消息"**（= 刚跟你说话那条），不用模型去猜 id；
- 要指定就传 `messageId`（聊天记录里每条消息前的 `#数字`）；
- `emoji` 可以不传（模型自己按语气挑），也可以传三种写法：
  表情本身 `👍`、Unicode 码点 `128077`、含义词 `赞` / `笑哭`；
- **显式指定的表情即使不在表情池里也照贴** —— 这是别人点名要的，
  拿池子白名单去拒绝用户请求是本末倒置；
- 一次最多 2 个；同会话 5 秒内连点会被拦住（防模型重复调用）；
- **不受概率/冷却/小时/日上限约束**：用户明确要求的事就该照做，
  否则又会出现"我让它贴它说贴不了"。但仍受协议端熔断保护。

同时加了一段提示词片段，直说"有人让你贴就直接调用工具，不要回『贴不了』"。

## 核心改动（v1.1）：从"随机凑数"改成"AI 按心情挑"

v1.0 是"每次从池子里随机抽 1 个"。实测在把概率临时调到 100% 的十分钟里，
它连着贴了 39 次，看起来就像"所有表情倾巢而出"。

v1.1 的做法：

1. **默认「AI 决定」**：把机器人刚发出的那句话交给模型，让它从表情池里挑 **0~2 个**；
   情绪平淡、正经回答问题、正在生气时，模型会回 `none` —— **一个都不贴**。
2. 一条消息最多 2 个是硬上限（`settings.maxEmojis` 被 clamp 在 1~2，配置写多大都不放行）。
   ⚠️ **v1.3 起这条已放宽成 1~5 可调** —— 用户要求"数值让我自己调"，锁死属于把旋钮焊死。
3. 触发频率也收紧了一档（见下表）。
4. 挑不到 / 模型调用失败 → 退回"随机 1 个"，**且不计入发送失败熔断**（这是两回事）。

三档模式：

| 模式 | 行为 |
|---|---|
| `AI 决定`（默认） | 按上面说的，让模型按心情挑 0~2 个 |
| `随机贴一个` | v1.0 的行为，随机抽 1 个 ｜ 不想花模型调用时用这个 |
| `关闭` | 插件保持加载但不动作 |

## 频率控制（四重闸门 + 并发保护，全部可调）

机器人每发出一条消息，**先摇一次概率**，只有摇中了才进入下面的闸门；
全过了才随机等 3~15 秒，把"贴哪几个"交给 AI/随机。

| 闸门 | 默认 | 说明 |
|---|---|---|
| ① 概率 | 20% | 每发出一条消息，有多大概率去"考虑"贴 |
| ② 会话冷却 | 300 秒 | 同一个群两次之间至少隔这么久 |
| ③ 每小时上限 | 3 次 / 群 | |
| ④ 每日上限 | 15 次 / 群 | 跨重启累计（落盘 `data/msg-reaction/state.json`） |

「一条最多贴几个」同样是可用旋钮（**1~5**，默认 2）—— 之前锁死在 1~2 等于把用户的旋钮焊死了，
现在只在 5 处封顶防止把整排表情占满。

另加：同会话并发保护（连着发两条不会重复计配额）、连续失败熔断（协议端不认时暂停 10 分钟）。

## 设置页：点选式表情池

设置页的「表情池」不再是让人看不懂的一串码点数字，而是一片**可以点的表情网格**：

- 点一下加入，再点一下移出；已选计数实时更新；
- 选中的套一圈实心高亮 + 右上角 ✓ 角标；
  **没选中的保持原色，绝不画成灰色** —— 灰色看起来像"被禁用/坏了"，会让人以为点了就发不出去；
- 「全选 / 清空 / 恢复推荐」三个快捷按钮；
- 最下面可以填自定义 Unicode 码点（如 `128077`）加进池子。

这背后是设置页新增的一个**通用字段类型** `emoji-pool`（任何插件都能用）：

```json
"emojiIds": {
  "type": "emoji-pool",
  "label": "表情池",
  "defaultIds": ["128077"],
  "pool": [{ "id": "128077", "label": "赞 / 同意" }]
}
```

值是**原来那串逗号分隔字符串**，存在一个隐藏 `<input data-key>` 里 ——
保存逻辑（按 `[data-key]` 读 `.value`）一行都没改，后端也不用动。

改动落在：
`ui/app/06-settings-render.js`（`emojiPoolHtml` / `bindEmojiPools` / `emoji-pool` 分支）
+ `ui/style.css`（文末 `.emoji-pool` 一节）。

## 技术实现要点（改代码前先看这里）

### 1. 触发是"观测出站"，不是挂钩子

本版核心**并没有真正调用 `after-tool` / `before-tool` 钩子**。实测同目录的
`typing-indicator` 同样收不到 —— 它是靠原型补丁工作的。本插件沿用那条被验证过的路：
**挂 `OneBotClient.prototype.call`**。

好处：所有出站发送都从这里过（文本/表情/图片/视频，核心工具/提醒/别的插件都算），
拿得到精确的 `group_id` 与回包里的 `message_id`。补丁**只观测**，原样返回原始 promise。

### 2. 补丁只装一次，逻辑走共享转发口 `G.dispatch`

热重载会 import 出**新模块实例**，但原型上的补丁是**旧实例装的、不会重装**。
如果补丁直接闭包旧实例的处理函数，改完代码热重载后跑的仍然是**旧逻辑**（要重启才生效）——
这个坑实测踩过（v1.0 → v1.1 升级后行为没变）。
所以补丁只做 `result.then(() => G.dispatch(...))`，而 `G.dispatch` 每次 `setup()` 都指向最新实例。

### 3. 日志必须走 `logger`，不能用 `api.log`

`api.log` 只是 `console.log('[skill:xxx]', ...)`，**不会写进 `data/logs/*.log`**。
用它等于出问题时没有任何线索（这个坑也踩过）。所以插件用 `src/logger.js` 的 `logger`。

### 4. 跨版本状态要"补字段"

`globalThis.__msgReactionState` 是跨热重载共享的，升级时它是**上一版留下的对象**，
新字段全是 `undefined`（例如 v1.1 新增的 `G.inFlight`）。
`setup()` 里的 `migrateState()` 负责补齐，否则新功能会静默失效。

### 5. AI 挑表情怎么调

走核心的 `chatCompletion`（与 `routes.js` 的 sticker-ai-label 同一个入口），
所以用户换渠道/换模型时自动跟着变，插件不需要另配 Key。
日志里以 `[req-fp] … [msg-reaction-pick]` 标签出现。
`maxTokens` 给到 600：会"先思考"的模型（gemini-3.8 等）额度给小了会把回话截断。

## 协议事实（来自 SnowLuma 源码，不是猜的）

```
POST /set_msg_emoji_like
{ message_id: <非零整数>, emoji_id: "<数字字符串>", set: true }
```

- `emoji_id` 长度 > 3 按 Unicode 码点当"大表情"处理，≤ 3 按经典 QQ 小黄脸编号处理。
- 目标消息必须在协议端 messageStore 里且带权威 sequence。**自己刚发的消息满足** ——
  SnowLuma 的 `finalizeSend()` 会当场 `cacheMessageMeta()` 登记。
- **仅群聊可用**：私聊会被协议端直接拒绝，插件会跳过。
- 接口存在性已实测：不存在的 id → `retcode=100 message not found`；
  不存在的 action → `retcode=1404 unknown action`。

## 排障

| 现象 | 先看这里 |
|---|---|
| 让它贴它却说「贴不了」 | v1.2 之前没有工具，属于设计缺口；现在应调用 `msg-reaction__react`。日志搜「按需贴」 |
| 表情还是贴得太频繁 | 先去状态面板看三行数：自动贴 / 被点名贴 / 拦下的。若"被点名贴"很多，说明模型没被拦住，检查设置里的「只有别人明说要贴时才允许模型贴」是否开着 |
| 有「拦截了一次…」 | 正常：模型想自己贴、但这个群里没人明说要表情，已拦下 |
| 点了名却没贴 | 判定规则刻意保守，换个说法再试（「给我贴个赞」「回我个表情」一定能过）。日志会有那次拦截的完整原因 |
| 概率调到 100% 却还是很少贴 | 先看面板的「跳过原因」。最可能是**会话冷却**（默认 300 秒：同一个群 5 分钟才贴一次），其次是每日上限。这两项跟概率是**互相独立**的闸门，都要一起调 |
| 一直没贴过 | 日志搜 `[msg-reaction]`。启动会打「已上线：AI 决定 · …」；没这行说明插件没加载 |
| 想确认它有没有"看见"发送 | 打开设置里的「排障：记录每条出站发送」，日志会逐条记录 |
| 想逐条看"为什么没贴" | 打开设置里的「排障：记录每次决策」，每次判频都会写一行含结果 |
| 「出站观测❌未安装」 | `src/onebot.js` 加载异常，检查核心文件是否完整 |
| 有「私聊…已跳过」 | 正常，QQ 协议不支持私聊表情回应（工具也会明确回一句"私聊贴不了"） |
| 有「AI 挑表情失败，这次退回随机」 | 模型通道那一次出了问题，会自动降级成随机 1 个 |
| 有「表情回应失败」 | `message not found` = 消息不在协议端缓存；`unknown action` = 协议端版本不支持 |
| 有「连续失败…暂停」 | 已自动熔断 10 分钟，多数是上面两种原因 |

## 自检

```bash
cd resources/app && node plugins/msg-reaction/selftest.mjs
```

30 项，全部离线：

- **自动路径**：概率闸门、会话冷却、每小时上限、概率 0、跳过名单、关闭档、
  AI 回 none（不贴也不算失败）、AI 挑多个后的上限截断、maxEmojis 可调 1~5、
  私聊跳过、**全链路**（起一个假的协议端 HTTP 服务，用真 `OneBotClient` 发一条消息，
  验证"发送 → 补丁观测 → dispatch → 贴表情"）、连续失败熔断、状态面板。
- **按需路径**：默认目标选择、emoji 三种写法、池外表情照贴、私聊报错、防连点、
  不受限频约束、指定 `messageId`。
- **v1.3 硬校验**（㉕~㉗）：11 条"这话算不算要表情"的正反例、没人要求时硬拦下、
  关掉开关后放行、按需贴不碰自动路径的配额（`lastReactAt` / `hourStamps` / `dayCount` 都不能被动）。
- **v1.4 数值真实性**（㉘~㉚）：同一条发送被打两次也只决策一次、没引用时退回贴自己那条、
  **概率校准**（设 50% 抽样 3000 次实测 50.2%）。

可注入的测试钩子：`state.transport`（假传输层）、`state.clock`（假时钟）、
`state.pickFn`（假的"挑表情"函数，替掉真模型调用）；
`internals.reactTool` 直接暴露工具定义，可以拿它的 `execute(ctx, args)` 单测。
