# Token 配额守卫（quota-guard）

按 **QQ 号**累计每个人每天消耗的 token，超额之后他的消息不再进模型；
一轮里所有参与者都超额时，**连模型都不调用**，一轮零消耗。
另有**总用量排行榜**，看全部历史谁烧得最多。

插件自身**不消耗任何 token** —— 全程只做本地读配置、比数字、做加法。

## 当日额度是怎么算的

一轮对话（从被触发到结束）内部可能包含十几轮 LLM 调用（每轮工具调用后都要再问一次模型）。
所以账是**按次记**的，不是按轮记：

| 时机 | 做什么 |
|---|---|
| `before-context` | 记下这一轮的参与者与各自发言条数（权重）；把额度已用尽的人从触发批里**剔除** |
| `after-response` | 每次模型返回后，把**这一次调用**的真实 `usage` 按权重分摊给参与者 |
| `chat.quota-gate` | 参与者全都超额 → 告诉核心"这一轮别发请求"，零消耗收尾 |

**权重口径**：某人在本次触发批里说了几条消息，就占几份。甲说 3 条、乙说 1 条，
这一轮的开销就是甲 3/4、乙 1/4。分摊用最大余额法，**各人之和精确等于实际消耗**，
不会因为四舍五入每天丢掉几十个 token 而对不上「用量」页。

**额度周期**：不是自然日。设 `resetHour = 4` 表示 04:00 到次日 04:00 算一天 ——
凌晨 3 点发的消息仍算"前一天"，与你设的"4 点刷新"预期一致。

## 三种被拦的情形

| 情形 | 结果 |
|---|---|
| 有人超额、还有人没超额 | 超额者的发言被剔除（不进提示词、不计他的账），**这一轮照常响应** |
| 参与者**全部**超额 | 核心跳过这一轮，**一条 LLM 请求都不发** |
| **发送限流已满**（每分钟/每小时条数用尽） | 同上，**一条 LLM 请求都不发**（见下节） |
| 档位本来就决定不回（如 1 档没被 @） | 不归本插件管，走核心原有的"没回话"路径 |
| 主动机会（冷场开话题，没人发言） | 不拦 —— 那一轮的开销不该记到任何人头上 |

## 发送限流前置（省掉白花的 token）

核心本来就有发送限流（设置里的「每分钟最多发送 / 每小时最多发送」）。但它原先
只在**真正发送那一刻**才拦 —— 而模型已经把话想完了。结果就是：

> 花了一次 token 让模型组织语言 → 发送时被限流挡回来 → 那句话白想了。

**本来就发不出去，根本不该问模型。** 所以本插件把这道检查提前到**请求模型之前**：

| | |
|---|---|
| 判定时机 | `chat.quota-gate`，位于提示词组装**之前**、任何 LLM 请求之前 |
| 数据来源 | 核心提供的 `sendState`（`sender.canSend(chatKey)` 的**只读**快照） |
| 拦下时 | 这一轮直接结束，**零 token 消耗**，会话状态记为「没回话」 |
| 开销 | 纯本地判断，插件自身不消耗任何 token |

**只读，不占额度。** `canSend` 只看不记；真正扣额度的仍然是发送那一刻的
`#checkRate`。所以"先问后发"之间不会重复计入，也不会因为问过就少算一条。
（测试里专门验了：连问 11 次，剩余额度一条不少。）

**不做"预留 N 条"的猜测。** 一次运行要发几条由模型决定，提前占额度会在模型少发时
白白浪费配额。所以只查"还能不能发**至少一条**"。真发到一半撞上限，剩下的会失败 ——
但前面那些已经发出去了，比整轮憋着不发好。

**可以关。** 全局设置里的「发送限流前置（推荐开）」，关掉就退回核心原有行为
（照常问模型、发送时才失败）。默认开。

> 依赖：核心需要提供 `sendState`。旧版核心不提供时，插件会**安全跳过**这项检查
> （不拦、不报错），其余功能不受影响。核心侧改动见 `src/sender.js` 的 `canSend()`
> 与 `src/orchestrator.js` 里 `chat.quota-gate` 附近。

## 配置

设置写在 `config.skills['quota-guard']`（与控制台设置同源）。绝大多数情况用页面改就行。

| 字段 | 默认 | 说明 |
|---|---|---|
| `resetHour` | `4` | 每日刷新时刻（0-23） |
| `defaultDailyLimit` | `0` | 没单独设额度的人用这个值；**0 = 不限** |
| `perUser` | `{}` | `{ "QQ号": { limit, note } }` 单独额度；`limit: 0` = 该人单独不限 |
| `notifyOnBlock` | `false` | 拦下后回一句话 |
| `blockWhenSendLimited` | `true` | 发送限流前置：分钟/小时发送额度用尽时，在请求模型之前就结束这一轮（见上文） |
| `notifyText` | `（今天的额度用完啦，明天再来找我吧）` | 提示文本 |

**额度为 0 = 不限**，但**不等于不统计**：不限的人也照常记用量，界面上看得见。
所以刚装好、什么都没配的时候，这个插件只是安静地记账，不会拦任何人。

---

界面分**两个页签**：

- **今日额度** —— 逐人管理当天的额度（主从布局）
- **总用量排行榜** —— 全部历史的总消耗排名

顶部还有一颗**总开关**（"已开启 / 已关闭"）。它和宿主「插件」页那个开关是
**同一个** `config.skills['quota-guard'].enabled`，不是另存一份 —— 在哪里切都行，
两边显示一致。关闭状态下页面上的用量数字仍会显示（那是账本），但顶部徽标会如实
写着「**未生效**」，因为这时候插件完全不工作：不记账、不拦人、不改任何行为。

## 页签一：今日额度

左侧是人员列表，点一个人，右边就是那个人的独立管理面板。

**左边（人员列表）**

- 每个人一行：昵称（或 QQ 号）、额度来源标签（`单独` / `默认`）、进度条、被拦次数
- 顶部工具条：搜索（QQ 号 / 昵称 / 备注）、筛选（全部 / 今天活跃 / 已设额度 / 未设额度 / 已超额）、排序（用量 / 剩余 / 昵称）
- 勾选框 + 全选 → 「批量设额度」一次给多个人设同一个额度
- 超额的行会高亮；统计条上的「已超额 N」可以直接点开筛选

**右边（单人管理）**

- 今日用量 / 额度 / 剩余、进度条、今天有没有发言、被拦次数、最后记账时间、额度刷新时刻
- **累计**：这个人的历史总消耗、总榜名次、占比（数据来自排行榜，见下）
- **额度模式**三选一：跟随全局默认 / 单独不限 / 单独设额度
- 额度输入框带常用值快捷按钮（10k / 50k / 100k / 500k / 1M / 不限）
- 备注（只给你自己看，不参与任何判定）
- 操作：保存这个人的设置 / 清零今天的用量 / 取消单独额度 / 删除这个人的记录

**添加人（三个页签）**

| 页签 | 说明 |
|---|---|
| **从群成员选** | 选一个群 → 拉出成员列表，点一下就把人带进"手填"框，填好额度点添加。**推荐用这个** |
| 从好友选 | 拉好友列表，同样点一下带进手填框 |
| 手填 QQ 号 | 直接敲号码；列表里都没有的人（比如还没发过言的群友）用这个 |

群成员列表优先显示**群名片**（群里实际看到的名字），没有名片才用昵称；
两种名字都能搜到，所以用真实昵称也能找到设了名片的人。大群人很多时列表最多
先渲染 300 个，用上面的搜索框缩小范围更快。

> 点列表里的人**不会**立刻把他加进去 —— 会先把 QQ 号和名字填进"手填"框，
> 你确认无误、填好额度再点「添加」。点错一下不至于就往额度表里塞个人。

## 页签二：总用量排行榜

按 QQ 号的**历史总消耗**排名。这是"总用量"，不是"一天的用量"，所以数据来源
和当日账本完全不同。

### 数据从哪来

来自**会话存档** `data/sessions/*.json`。每个会话文件都完整记着：

- `usage.totalTokens` —— 这一次运行烧掉的 token（真实计费量）
- `trigger[]` —— 本轮触发批，每条带 `senderId`（QQ 号）

这正是分摊所需的全部信息，而且**是历史数据** —— 插件可能是刚装的，但会话存档
从更早就存在，所以排行榜**立刻覆盖全部历史**，不用等它慢慢攒。

分摊口径与即时记账完全一致：把这一轮的总消耗按各人发言条数分摊。

### 榜上有什么

- 名次（前三名有奖牌）、QQ 号、昵称、累计 token、**占比**、参与会话数、发言条数、今日用量
- 搜索（QQ 号 / 昵称 / 备注）、排序（总用量 / 占比 / 参与会话 / 发言条数 / 昵称）
- 每行有「去设额度」按钮，一键跳到今日额度页并选中那个人
- 顶部统计：总计 token、上榜人数、归到人头的会话数、模型调用次数、**未归到人头**的部分
- 「重新统计」按钮：忽略缓存全量重扫（只读存档，不改任何数据）

### 几个口径说明

**「未归到人头」是什么？** 有些会话花了钱但没人可归 —— 比如主动开话题
（群里没人说话，机器人自己找话题）。这部分**确实花掉了**，会计入总计，
但不该记到谁头上。界面把它单独列出来，这样"各人之和 + 未归人 = 总计"
始终成立，账对得上。

**占比的分母**是"归到人头的那部分"，不是全部消耗。否则没人发言的会话会把
所有人的占比一起拉低，看起来像算错了。

**机器人自聊**（`private:<机器人QQ>`）整段跳过，不归任何人 —— 但它的消耗
仍计入总计。跳过次数在页面上如实列出。

**首次打开要等几秒**：第一次会扫描全部会话存档（实测 757 个文件约 5.7 秒），
所以做成**后台分片扫描**，页面显示"正在统计…"并自动刷新，不会卡住界面。
扫完之后每次进入页面只要约 **20ms**（只补扫新会话）。

### 数据存哪

与当日账本**分开**存在 `data/quota-guard/cumulative.json`。
两份账本的字段说明见文末的[数据存哪](#数据存哪)。

## 用量按 k 计数

界面上所有 token 数字都用 **k / M** 显示，读起来不用数零：

| 原始值 | 显示 |
|---|---|
| 999 | `999` |
| 1 000 | `1.0k` |
| 15 500 | `15.5k` |
| 99 999 | `99.9k` |
| 150 000 | `150k` |
| 999 949 | `999k`（高位向下取整，不会出现 `1000k`） |
| 1 234 567 | `1.2M` |

**这只是显示层的换算。** 账本里存的、配置里写的、发给后端的，一律还是精确整数 ——
否则每显示一次就四舍五入一次，账会越算越偏。鼠标悬停在数字上会给出精确值
（例如 `15,500 token`）。

**输入也支持简写**：额度框里可以直接写 `50k`（= 50000）、`1.5k`（= 1500）、
`2m`（= 2000000），带逗号也行，大小写都认。边输边在下面显示换算结果，
免得把 500000 手滑写成 5000000。填了看不懂的内容会明确报错，不会静默存成 0。

> 说明两处刻意的设计：
> **① 一个人什么时候会出现在列表里？** 有单独额度的人 ∪ 今天有账的人。
> 所以「取消单独额度」之后，如果他今天也没发过言，就会从列表里消失 —— 不是丢数据。
> **② 昵称和备注是两回事。** 昵称是账本记下的真实群名片，只有他今天发过言才知道；
> 备注是你自己写的标签。没昵称时界面用备注兜底显示，但两者在数据上始终分开
> （`name` / `note` / `displayName` 三个字段），免得改个备注就像换了个人。

数据全部来自插件的 `handleUiRequest`，页面不自己算账 —— 保证
「界面显示的」和「实际生效的」同源。界面里不使用原生 `prompt` / `confirm`
（宿主在 Windows 上刻意弃用了原生对话框，关闭后窗口不回焦会导致输入框打不了字）。

## 数据存哪

两份账本，都在 `data/quota-guard/` 下（`data/` 即程序实际使用的数据目录，
多实例时是 `data-1/`、`data-2/`…）。**分开存是刻意的**：当日账本在每次发言、
每次回复时都被高频读写，把一份可能很大的累计表塞进去，会让那条热路径
每次都要序列化整张表。

### `ledger.json` —— 当日用量

（下面的数字与 QQ 号都是**示例假数据**）

```json
{
  "version": 1,
  "users": { "10001": { "dayKey": "2026-01-01", "used": 120000, "name": "示例用户" } },
  "totals": { "2026-01-01": 120000 },
  "blocked": { "2026-01-01": { "10001": 3 } }
}
```

按天存 `dayKey`，跨天自动视作 0（不需要定时任务去清）。

### `cumulative.json` —— 历史累计（排行榜用）

```json
{
  "version": 1, "updatedAt": 1700000000000, "scannedOnce": true,
  "users": { "10001": { "tokens": 1200000, "sessions": 30, "messages": 120,
                        "name": "示例用户", "firstAt": 0, "lastAt": 0 } },
  "totals": { "tokens": 5000000, "calls": 200, "sessions": 60 },
  "skipped": { "selfChat": 0, "noUsage": 1, "noTrigger": 0 },
  "processed": { "<会话文件名>": 1700000000000 }
}
```

`processed` 记着每个会话文件的 `mtime`，文件没变就跳过 —— 增量扫描就是这么来的。
删掉整个文件会触发一次全量重扫（也可以点页面上的「重新统计」）。

**两份账本损坏或不存在都从空账开始，绝不抛错** —— 记账失败不该让聊天主流程崩掉。
出问题时删掉对应文件即可，它只是缓存/账本，删了会重建。

## 依赖的核心扩展点

本插件的"零消耗"依赖核心里的一个能力：`chat.quota-gate`
（见 `src/orchestrator.js` 的 `#runAgent`）。

- 返回 `{ skip: true, reason }` → 核心在**组装提示词之前**结束这一轮，一条请求都不发
- 返回 `null` → 核心照常往下走
- **没装 / 没启用本插件时，核心那段代码是空操作**，行为与没有这套机制时完全一致

> ⚠️ 这个能力是随本插件一起加进核心的。如果你把 `resources/app/` 换回旧版本、
> 或重装 QQ Agent，核心里就没有这个扩展点了 —— 那时本插件会**只记账、不拦人**
> （`before-context` 仍会把超额者剔除，但整批超额时模型还是会被调用一次）。
> 恢复办法：重新应用核心改动，或参考 `src/orchestrator.js` 里
> `chat.quota-gate` 附近的注释。

## 已知取舍

- **剔除是"标已读"**：被剔除的消息仍留在会话存档里（作为历史上下文，
  它们仍可能出现在后续轮次的【已读信息】里），只是不参与这一轮的触发与分摊。
- **超额即封顶**：用量最多记到额度值，不会继续累加。好处是界面不虚报
  （额度 100 却显示 300 会让人以为没生效）；代价是看不到"超额了多少"，
  只有 `blocked` 里的拦截次数能反映。
- **删除的会话记录不影响账本**：账本独立存在 `data/quota-guard/`，与会话存档无关。
