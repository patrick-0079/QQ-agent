# CHANGELOG — Steam 查价（steam-query）

## 1.2.2 / 2026-10-03 / 卡片配色改成**下拉选择**

- `theme` 的 `configSchema` 从 `type: "string"` 改成 **`type: "enum"` + `values: ["dark","light"]`**
  → 控制台里不再是让人手打的输入框，而是下拉。版本号 1.2.1 → **1.2.2**。
- **为什么**：1.2.1 刚加这个字段时是字符串，而字符串很容易被填成 `Light` / `深色` / `light `（带空格）。
  虽然代码里做了容错（`themeOf()` 会 trim + 转小写，认不出的一律按深色），
  但**用户填错了是没有任何反馈的** —— 下拉能把这类输入错误从根上消掉。
- **代码一行没改**：enum 选出来仍是 `"dark"` / `"light"`，`themeOf()` 照旧。
- 与 `ai-status`（面板配色）、`weather-card`（卡片配色）统一成同一种控件（三处都是下拉）。

## 1.2.1 / 2026-10-03 / 卡片支持**明暗主题**（配置里选 dark / light）

### 改了什么

- 新增配置 `theme`：`dark`（默认）/ `light`，与 weather-card、mc-status 同款做法
  （`type: string` + 说明，不搞下拉）。
- 版本号 1.2.0 → **1.2.1**。

### 配色不是简单反色

深浅两套的**折扣绿和品牌蓝是分别调的**：

| | 深色（卡底 #1a2029） | 浅色（卡底 #ffffff） |
|---|---|---|
| 折扣绿 | `#a4d007`（Steam 亮绿） | `#4f8a00`（压暗，亮绿在白卡上看不清） |
| 品牌蓝 | `#66c0f4`（提亮） | `#1b6ab8`（压暗，否则发飘） |
| 折扣标签底 | `#2a3a0f`（暗绿） | `#e8f4d4`（浅绿） |
| 正文 | `#c6cedb` 浅字 | `#3a4453` 深字 |

**另外窗口背景色（`backgroundColor`）也必须跟着主题走** —— 它是用来兜住亚像素误差的，
浅色卡配深色窗口边框，截出来会在右边/下边露出一圈深边（weather-card 的注释里记过这个坑）。

### 顺手修掉的一个小 bug（测试抓到的）

初版只有 `readSettings()` 做了 trim + 转小写，而 `buildCardHtml()` 里是直接比较
`s.theme === 'light'` —— 于是传 `' LIGHT '` 会掉进深色分支。
真机上表现为"我明明填了浅色，卡片还是黑的"。
现在判据抽成 `themeOf()`，`readSettings` / `buildCardHtml` / `renderPng` **三处共用同一个**，
填 `light` / `Light` / ` light ` 都能认；认不出的值（含拼错、空）一律按深色，不会把卡片弄成没配色。

### 验证

`node test/steam-query-test.mjs` → **64/64**（新增 3 条：深浅底色与文字色相反且折扣绿两套不同、
大小写/空格容错、`readSettings` 只认 light）。

## 1.2.0 / 2026-10-03 / 修卡片右侧大片空白 + 支持**一次查多个游戏**

### 一、卡片右边为什么空一半（主人报障）

| | weather-card（对照） | 本插件（改前） |
|---|---|---|
| `CARD_W` | 720 | 320 |
| HTML 里 body/card 宽 | **720（= CARD_W）** | 320 |
| 窗口宽 | `CARD_W * 2` | `CARD_W * 2` |
| 结果 | 内容 720 装进 1440 窗口 | 内容 320 装进 640 窗口 → **右边 320px 全空** |

**根因**：我当初抄 weather-card 的离屏渲染骨架时，**只抄了 `CARD_W * 2` 这一半**，
没注意它配套的 HTML 也把宽度写成了 `CARD_W`（两边数字对得上才不空）。
现在：
- `CARD_W` 320 → **480**（宽一点排版更从容）；
- 窗口宽度与 `setContentSize` 都用 **`CARD_W`**（贴着内容开，不再乘 2）。

并加了一条**源码级断言**防回归：代码里不许再出现 `width: CARD_W * 2`
（只扫代码行、跳过注释 —— 注释里留着这个反例讲坑在哪）。

### 二、一次查多个游戏

```
\steam 死亡搁浅2,死亡搁浅,地铁:离乡
```

- 分隔符：逗号 / 顿号 / 分号（全角半角都认），**最多 5 个**（再多就成刷屏了）。
- ⚠️ **绝不按空格拆** —— 游戏名里带空格是常态（`Death Stranding 2`），按空格拆会把一个名字劈成两半。
- ⚠️ **冒号不拆** —— `地铁:离乡` 的冒号是官方名字的一部分。
- 排版：**1 个游戏** → 详细卡（含 Metacritic / 开发 / 简介）；
  **多个** → 紧凑卡，每个游戏一块、块间一条分隔线（多堆字段会长得没法看）。
- 查不到的游戏会**单独列一行**（"没查到的：xxx"），不静默吞掉。

### 三、实现时踩到的两个真坑（都靠真机实测才发现）

**① `appdetails` 的批量查询必须带 `filters`**
我原以为"批量传 appid 更快"，写了 `fetchDetails([a,b,c])` —— **HTTP 400**。
实测：`&appids=1,2,3` **只有配合 `&filters=price_overview` 时才成立**
（打折播报正是这么用的，所以一直没暴露）；
不带 filters 传多个，Steam 直接拒。现在改成**逐个查**（5 个游戏 5 次请求，稳）。
⚠️ 这个坑很阴：报出来是 "HTTP 400"，长得像"Steam 挂了"，其实是自己把请求拼错了。

**② 同一个游戏会被两个关键词解析到、在卡上出现两遍**
实测国区搜「死亡搁浅」**只返回一条结果，就是「死亡搁浅2」**（原作在国区商店不可见），
于是 `${'死亡搁浅,死亡搁浅2'}` 两个词都指向 appid 3280350 → 卡上同一个游戏出现两次。
已按 appid **去重**（并记一条日志说明"某某解析到的是「YY」，与前面重复，跳过"）。

## 1.1.5 / 2026-10-03 / 取参取错条目：批内后续消息把指令挤掉了（"下了指令却回帮助"）

### 现象

主人发 `\Steam 死亡搁浅2`，控制台里 finishReason 明明写着
**"指令直达（steam-query / steam-query__steam_query）"**，但群里收到的是**帮助页**；
而且控制台的"触发"一栏显示的是 **`[你已被移出群聊]：[图片]`** 而不是那条指令。

### 根因

那条会话的实际触发批是**三条**消息：

```
1. '我准备眠了（）'
2. '@机器人 \Steam 死亡搁浅2'    ← 指令在这（原文带真实 QQ 号，已隐去）
3. '[图片]'                                   ← 别人紧接着发的
```

`fullBodyFrom()` 取的是"批内**最后一条**非自己消息" → 拿到 `[图片]` →
里面没有 `\steam` → 返回空串 → 走到 `if (!raw) return usageText()` → **回帮助页**。

**关键在于门槛和取参是两套规则**：
指令门槛判的是"**批内任意一条**命中"（`batchHitAnyCommand`），而这里取参只看**最后一条**
—— 两条规则不一致，就会稳定地产生"**认了指令、却拿不到内容**"的半残状态。
群里消息本来就是成批到达的，所以用户发完指令后只要有人接一句话或发张图，就必然踩中。

### 修法

从后往前找**含这条指令的那一条**（`[...list].reverse().find(...)`），
`[图片]`、纯聊天会被跳过。批内有多条指令时仍然取最后一条（用户改口优先）。

### 这是同一个坑第三次

| 插件 | 状态 |
|---|---|
| `agent-task` | 早已修（它的 `commandEntryFrom` 就是这个思路） |
| `steam-query` | **本次修** |
| `netease-song-id` / `pc-control-l3` | 查到 `fullBodyFrom` 是**一模一样的写法**，本次一并修（见各自 CHANGELOG） |

### 验证

`node test/steam-query-test.mjs` → **56/56**（新增 2 条：用**真实的那条触发批**做样本，
断言能取到 `死亡搁浅2`；批内多条指令取最后一条）。

## 1.1.4 / 2026-10-03 / **致命修复**：出图时静默不发送（查游戏"没反应"的真凶）

### 现象

主人报障："查死亡搁浅二却无返回"。查消息存档确认：`01:02:50 [群] \Steam 死亡搁浅2`
之后**没有任何机器人消息**，日志里也**一行 `[Steam]` 业务日志都没有**。

### 根因（我自己的设计错误）

早先 `runQuery` 出图时是这么写的：

```js
if (png) return { image: png, caption: '', _directText: null };   // ← 错的
```

而**指令直达链路只认 `_directText` 和 `_cardSent`**
（`src/skills/command-router.js` 的 `pickDirectText`），**根本不认识 `image` 字段** ——
它拿到这个返回值后判空串 ⇒ `if (text)` 不成立 ⇒ **一条都不发**。

**为什么极难自查**：

- 失败路径（网络错）返回的是 `_directText`，**照常会回文字** —— 所以"报错能看见"；
- 只有**成功出图**这条路径静默无返回，群里表现为"查了没反应"；
- `renderPng` 在纯 node 下必然返回 null（没有 Electron），所以**离线测试永远走不到这个分支**，
  54 条测试全绿也照样漏掉它。

### 改了什么

- 改成与 mc-status / weather-card 一致的姿势：**工具内自己 `await ctx.sender.sendImage(...)`**，
  成功则返回 `{ content, _cardSent: true }`；发送失败则记日志并**降级成文字**（不让用户什么都收不到）。
- 没有 sender 的场合（老框架 before-context 兜底）也走降级文字。
- 版本号 1.1.3 → **1.1.4**。

### 附带澄清（不是 bug）

同一批日志里 `00:58:37 \steam 绑定 <SteamID64>` 看着也"没回"，**其实发了**：

```
00:58:40 [发送 -> group:123456789] ✅ 绑定成功：Oh（76561199816756385）
```

是消息存档与我 grep 的时间窗对不上造成的误判。**真凶只有出图这一条。**

另外这次也**反证了 1.1.2 的 net.fetch 适配是有效的** —— 01:02 那次查询是在
Steam 加速器劫持状态下**真的查到了数据**（否则会走失败路径回错误文字），
说明 `net.fetch` 走 Chromium 栈确实穿透了本地反代。

### 验证

`node test/steam-query-test.mjs` → **54/54**（新增 1 条**源码级**断言：代码里不许出现
`return { image: ... }`、必须调 `ctx.sender.sendImage`、必须返回 `_cardSent: true`。
只扫代码行、跳过注释 —— 注释里特意留了那个错误写法当反例）。

## 1.1.2 / 2026-10-03 / 请求改走 **Electron 网络栈**（能穿过 Steam 加速器的本地反代）

### 背景

1.1.1 里查明：开着 Watt Toolkit（Steam++）时，hosts 把 Steam 域名指向 `127.0.0.1`、
   由它的进程监听 80/443 做反代，Node 的 fetch 不认那张证书 → 所有请求全失败。
   当时给的方案是"关掉加速器的网络加速"，但很多人是**故意开着**的（Steam 下载、社区页都要它）。

### 改了什么

- 新增 `getFetch()`：请求**优先用 Electron 的 `net.fetch`**，拿不到才退回全局 `fetch`。
  版本号 1.1.1 → **1.1.2**。

### 为什么这样能解决

`net.fetch` 走的是 **Chromium 的网络栈**，而 Chromium 在 Windows 上**使用系统根证书库** ——
加速器把自己的 CA 装进了系统（这正是浏览器里一切正常的原因），所以 Chromium 认它。
Node 自带的 fetch 用的是 undici + **内置 CA**，不读系统库，于是不认。

一句话：**用户在浏览器里能打开 Steam，不代表插件能用** —— 两者根本不是一个 TLS 栈。

⚠️ 另外确认过 `NODE_USE_SYSTEM_CA=1`（让 Node 读系统证书库）**在本项目用不了**：
Electron 内置的是 **Node 20.18.3**，而这个变量要 Node 22.15+ 才有。

### 风险与保底

- 拿不到 `electron.net` 时（纯 node、离线测试）自动退回全局 fetch，
  所以测试里打桩 `globalThis.fetch` 依然有效（实测 52/52 不受影响）。
- 如果 `net.fetch` 也过不去（例如加速器自己就是坏的），用户仍可关掉加速器的
  「网络加速」——那条路是**确定有效**的（23:35 直连实测 8/8 全通）。
- 兜底提示已写明这一点：证书类错误会直接告诉用户"多半是开着 Steam 加速器"。

### 验证

`node test/steam-query-test.mjs` → **52/52**（打桩仍走全局 fetch，未被影响）。

## 1.1.1 / 2026-10-03 / 密钥真机验证通过 + 资料不公开时说清原因

### 密钥验证（用户配好 key 后实测）

配置里拿到密钥（**开头带了个空格**，`readSettings` 的 `.trim()` 已经处理掉，
功能不受影响），绕过本机证书问题后逐项实测：

| 接口 | 结果 |
|---|---|
| `ResolveVanityURL` | ✓ 685ms，`gaben` → `76561197968052866` |
| `GetPlayerSummaries` | ✓ 249ms，返回 `Rabscuttle`（状态 离线 / 公开资料 否） |
| `GetOwnedGames` + `GetSteamLevel` + `GetRecentlyPlayedGames` | ✓ 993ms（该账号资料不公开，故游戏库为空） |
| 对照：`storesearch`（免密钥） | ✓ 617ms |

结论：**密钥有效，需密钥的接口全部可用。**

### 改了什么

- `\steam 我的`：资料不公开时，游戏库/时长/最近游玩必然是空的，
  现在会明确补一句「你的 Steam 资料不是公开的……」并给出改成公开的路径。
- **证书类错误的提示改成可操作的**：之前只说"本机 TLS 证书验证失败"，
  现在直接点名最常见的原因（见下），并说明怎么自查、怎么处理。
- 版本号 1.1.0 → **1.1.1**。

### 顺手查清了"本机 TLS 失败"的真正原因（是加速器）

本轮实测时发现本机对 Steam 全域名 `UNABLE_TO_VERIFY_LEAF_SIGNATURE`，追下去发现：

- `%WINDIR%\System32\drivers\etc\hosts` 里有 `# Steam++ Start` 段，
  把 `store.steampowered.com`、`steamcommunity.com`、`media.steampowered.com` 等
  **全部指向 `127.0.0.1`**；
- `Steam++.Accelerator.exe` 正监听 **80 / 443**，做本地反代；
- hosts 的修改时间是 **2026-10-02 23:56** —— 正好在"23:35 实测 8/8 全通"之后。

**结论：是 Steam 加速器（Watt Toolkit / Steam++）劫持了流量并替换了证书**，
Node 不认那张证书。这是**用户机器上的软件行为**，不是插件的问题、也不是 Steam 挂了。

⚠️ 影响面要说清楚：QQ Agent 的插件跑在主进程、用的是 **Node 的全局 fetch**（undici），
和我做诊断时用的是同一套 TLS 栈，**所以群里调用同样会失败**。
（Electron 只有渲染进程的 fetch 才走 Chromium 栈，插件用不到。）

**处理**：关掉加速器的「网络加速」，或把 steam 域名加进直连规则。
Steam 商店与 API 在国内通常能直连（23:35 那次 8/8 就是直连实测的），
只有社区页 `steamcommunity.com` 才需要加速。

### 为什么

上面那轮实测正好撞上这个分支：`gaben` 账号 `communityvisibilitystate=1`（非公开）
→ `GetOwnedGames` 返回空 `response`。此时 `\steam 我的` 只会输出昵称 + 状态，
**游戏库那几行直接消失**，用户看到的是"什么都没有" —— 不解释的话会以为插件坏了。
（`bindReply` 早就有这个提示，`myProfileReply` 漏了，属于同类问题只修了一处。）

### 验证

`node test/steam-query-test.mjs` → **52/52**（新增 2 条：不公开时要给提示、
公开时正常显示等级/游戏库/最近游玩且不出现该提示）。

### 来源

### 改了什么

- 新增三个口头指令（都走指令直达，0 token）：
  - `\steam 关注 <游戏名|appid>` —— 名字会自动解析成 appid 再存，这样播报时不用每次重搜
  - `\steam 取关 <游戏名>` —— 支持**部分匹配**（打"艾尔登"也能取关"艾尔登法环"）
  - `\steam 关注列表` / `\steam 列表` —— 同 `\steam 打折`
- 别名一堆，尽量让"口头"说得出口：关注 / 订阅 / 盯一下 / watch / add；
  取关 / 取消关注 / 不关注了 / 移除 / 删掉 / unwatch / remove / del。
- 关注成功会**顺手报一句当前价格**（"已关注《X》 ¥298"），而不是干巴巴一句"已关注"。
- 重复关注不重复加；取关失败会**列出当前关注了什么**让用户挑，不是只说"没有"。

### 为什么关注列表要"配置 + 口头"两份（关键设计）

口头关注**不写回配置**，而是落 `data/steam-query-state.json`。原因：
- 插件改配置要走 `POST /api/config`，直接改 `data/config.json` 不生效
  （内存有缓存，而且控制台旧页面一保存就覆盖回去 —— 项目真实踩过这个坑）；
- 口头关注和「绑定表」一样属于**运行时数据**，落 state 更自然。

最终列表 = `(配置 watchList + state.watch) − state.hidden`

**`hidden` 这一层是必需的**：没有它就出现"取关不掉"——用户在群里取关了一个
控制台配的游戏，下次播报它又冒出来，看起来就像取关功能坏了。
重新 `关注` 时会自动把 hidden 里的痕迹清掉，否则会出现"加了但列表没变"。

### 顺手修掉的一个可用性缺陷

`\steam 关注列表` 在"都没打折"时只回一句"当前都没有打折" —— **整条回复里一个游戏名都没有**。
用户打这个命令是想确认"我关注了啥"，等于没回答（实测所见）。
现在手动查会**把没打折的也列出来**（带价格，最多 15 个）；而自动播报仍然只列达线的，
不然每天推一堆没打折的纯噪音。

### 错误提示：证书类故障要说清"不是 Steam 的问题"

`shortError` 原先只读 `error.message`，而 undici 把真实原因包在 `error.cause` 里 ——
所有网络/TLS 故障都会显示成笼统的 `fetch failed`。
2026-10-03 实测遇到 `UNABLE_TO_VERIFY_LEAF_SIGNATURE`（本机网络在 TLS 层就失败，
curl 同时报 `CRYPT_E_NO_REVOCATION_CHECK`，即**证书吊销检查连不出去**），
表现是**所有请求 0ms 立即失败**，很像"插件坏了"。现在会明确说：
「本机 TLS 证书验证失败（网络环境受限）—— 不是 Steam 的问题」。
`scripts/check-steam.mjs` 也加了同款判断，一次性把五类域名的结果汇总成结论。

### 验证

`node test/steam-query-test.mjs` → **50/50**（新增 12 条：关注落盘与追溯、重复关注、
搜不到、参数缺失、取关+hidden、部分匹配、取关不存在的、**取关配置里的项也要生效**、
取关后再关注能恢复、三个别名、配置与口头合并、没打折的也要列出）
`check:privacy` / `check:undef` / `npm test` 全绿。

> ⚠️ 本轮**没做成真机联调**：跑的时候本机网络正好在 TLS 层失败（见上）。
> 同一条链路 40 分钟前是通的（那时实测：赛博朋克 2077 ¥89.40 / 好评率 87%），
> 所以功能本身没问题，是环境在波动。

## 1.0.0 / 2026-10-02 / 首个版本：查价卡 + 打折播报（零密钥）+ 玩家功能（需密钥）

### 来龙去脉

用户问"Steam 有 API 可以调用吗"，并要求"先检查一下网络可不可行然后再做"。
所以先做了一轮**连通性实测**（结论见下），确认可行才动手。

### 连通性实测结论（本机，node 原生 fetch）

| 端点 | 实测 | 判定 |
|---|---|---|
| `store.steampowered.com/api/appdetails` | 8/8，270~1055ms | ✅ 稳定 |
| `store.steampowered.com/appreviews` | 5/5 | ✅ 稳定 |
| `store.steampowered.com/api/storesearch` | 稳定 | ✅ 稳定 |
| `api.steampowered.com/*` | 5/10，**整轮全挂或全通** | ⚠️ 间歇 |
| `steamcommunity.com/dev/apikey` | 0/10，超时 | ❌ 不通（申请密钥的页面） |

**⚠️ 最大的坑：curl 测出来的结论是反的。** 终端里存在 `http_proxy` 时 curl 会走代理，
测到的是代理的通断；而 QQ Agent 是普通 Electron 进程，undici **默认不走代理**。
同一 URL：curl 说半数超时，node fetch 说 8/8 全通。
→ **以后测外网连通性一律用 node 原生 fetch。** 工具落在 `scripts/check-steam.mjs`。

### 改了什么

- 新增本插件。指令 `\steam`，走**指令直达**（0 token、不过模型）：
  - `\steam <游戏名|appid>`：查价格 / 折扣 / 好评率 / Metacritic / 发售日 / 平台 / 简介
  - `\steam 打折`：查关注列表当前折扣
  - `\steam 绑定 <自定义ID>` / `解绑` / `我的` / `谁在玩`（需密钥）
- 输出**图片卡片**（离屏 BrowserWindow 渲染，骨架与 weather-card / mc-status 一致），
  渲染不可用时自动降级成纯文字 —— 绝不因为"图没出来"就什么都不发。
- **打折播报**：填关注列表 + 群号 + 时间，每天定时批量查价，折扣到线自动播报。
  关注列表支持**游戏名**（自动解析成 appid 并落盘缓存）或 appid。
- **开黑播报**（需密钥、默认关）：定时看绑定的群友有没有开始玩新游戏，有就报一句。

### 为什么坚持零密钥可用

Steam 的数据分两套：**商店接口**不需要任何认证（商店前端自己就在用），
**官方 Web API** 查玩家数据才要 key。而 `steamcommunity.com`（申请 key 的页面）本机不通
—— 如果核心功能依赖密钥，这个插件在用户申请到 key 之前就是块砖。
所以查价与打折播报做成**完全不依赖密钥**，玩家功能作为可选增强。

### 实测踩到的四个坑（都写进代码注释了）

1. **`/search/results/?json=1` 拿不到 appid**：它的 `items` 里只有 `name` 和 `logo`，
   看着像能用，实际没有 id。搜游戏必须用 `/api/storesearch/`（上限 10 条）。
2. **价格是整数分**：29800 是 ¥298.00，要除 100。
3. **免费游戏没有 `price_overview` 字段**（Dota2 / CS2 都没有），不先判 `is_free` 会崩。
4. **`filters=price_overview` 批量查询时不返回 `name`** —— 所以打折列表里的名字
   优先用关注列表里记的，而不是从响应里取。

### 一次静默失败（值得记）

初版写完后测试报"绑定表里读不到刚写的数据"。根因是：**`fs` / `path` / `os` 三个模块
根本没 import** —— 而所有用到它们的地方都在 `try/catch` 里（`writeState`、`renderPng`），
于是错误被吞掉，表现成"绑定成功但下次读不到""卡片渲染失败自动降级成文字"。
**功能看着正常，实际全在静默降级。**
教训：`catch` 里只 `log` 不抛，会把"模块没 import"这种硬错误伪装成"偶发失败"。

  重试、限频、子命令分流、密钥缺失提示、绑定落盘、HTML 转义、开黑去重）
