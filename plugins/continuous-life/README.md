# 持续的生活（continuous-life）

一个**确定性插件**：在设定的时间段内，按间隔给机器人**开一轮「空闲唤醒」**。
没有人说话也照样开轮，让模型自己决定这一轮做什么。

**它只负责开轮**。发不发消息、调不调技能（包括刷空间、开浏览器）全由她自己决定；
什么都不做就不发消息。插件不代她执行任何动作。

## ⚠️ 注意事项（装之前先看这一节）

**1. 需要宿主支持，否则「已启用但不工作」**
本插件依赖宿主提供的「空闲唤醒」能力（能力名 `session.idle-wake`）。
宿主不支持时，能力查表会把本插件过滤掉，宿主**根本不会来问它** ——
表现为插件页显示「已启用」，但到点毫无反应。
装之前请先确认你的宿主版本支持该能力；较旧的宿主需要先在宿主侧加入该接口。

**2. 只装插件、不重启宿主，核心不会来问它**
插件自身的改动是**热重载**的（改设置、改提示词立即生效）；
但宿主侧支持这段能力属于**核心代码**，热重载不会重新加载已经 import 的 `src/` 模块。
所以：**首次安装、或宿主更新后，必须完整重启一次宿主。**
判断办法：看状态面板的「核心是否在询问」——显示「还没被问过」就是这个原因。

**3. 默认是关的**
`enabledByDefault: false`。不手动打开总开关，插件完全不动：不询问、不开轮、不消耗 token。

**4. 它只开轮，不替她说话**
这一轮说什么、调不调技能，由模型自己决定；模型什么都不做就不发消息，
插件也不会补一句「我结束了」（控制台记的「本轮未发消息」是**记录**，不是发言）。

**5. 建议从小额度起步**
先按默认的「间隔 120 分钟、每天 5 次」跑几天，确认行为符合预期，再按需调紧。
`minIntervalMinutes` 有 30 分钟下限；`maxPerDay` 上限 100。

**6. 不会打扰正在进行的对话**
已经有人在等回复（有未读消息、或这一轮正在跑）时会**跳过这次唤醒，且不计入当天次数**。

**7. 隐私**
不发送任何消息、不发起任何网络请求；不读取聊天记录文件、剪贴板或用户文件。
只在本地写 `data/continuous-life.json`（每个群的上次唤醒时间、当天次数、上次结果）。

## 怎么用（四步）

1. **装好并重启宿主**（见上面注意事项 1、2）
2. 打开插件页里的 **「启用持续的生活」** 总开关
3. 设好 **时间段 / 最小间隔 / 每天次数**
4. 按需要在 **「唤醒说明」** 里写她这一轮实际看到的提示词
   （只替换【未读信息】那一段，前面的记录/记忆/规则不动）

装完想确认它在干活：看状态面板的「核心是否在询问」「上次唤醒」「未唤醒原因（抽样）」。

## 为什么必须是插件、以及为什么核心需要加一个接口

按项目判据：**规则能写死 → 插件；要理解人话 → 技能**。这里的规则全是能写死的
（时间段、间隔、每天次数、0 点清零），所以是插件（`plugins/`）。

但插件有一个绕不过去的限制：扩展靠 `registerTool` 与 `hooks` 工作，
**工具要模型调用才生效，钩子只在某一轮已经跑起来之后才触发** —— 没有新消息就没有轮次，
钩子永远不触发。而"开一轮"的入口 `orchestrator.wake()` 是核心私有的调度方法，
没有暴露给扩展（也没有 wake 类能力、没有对外的 wake 端点）。

所以核心加了一个很小的接口（约 40 行），方向与项目既有约定一致 ——
**核心按能力名取用，不认识任何具体插件**：

```
能力名 session.idle-wake
核心每 30 秒问一次：provider({ chats, runningChats, paused }) → chatKey | chatKey[] | null
核心拿到 key 后自己去调 wake(chatKey, { proactive: true })   ← 开轮的动作始终在核心手里
```

关掉或卸载本插件 → 核心的能力查表自动过滤 → 核心那边零残留。
没有插件提供该能力时，核心的询问等于空转（一次内存查表 + 一次同步函数调用）。

⚠️ **这个核心改动要重启 QQ Agent 才生效**（热重载只重载 `skills/`、`plugins/` 下的扩展，
不会重新加载已经 import 的 `src/` 模块）。插件本身的改动是热重载的。

## 行为

- 只在**开始时间到结束时间**之间运行，时区跟随系统。默认 08:00–20:00。
  结束时间早于开始时间时按跨零点理解（如 22:00–06:00）；起止相同 = 不限时间。
- 两次唤醒至少间隔 N 分钟，默认 120（下限 30）。
- 每个群每天最多 M 次，默认 5（范围 1–100）。过了 0 点重新计数。
- **到点只开一轮**。两次唤醒之间不会再开第二次。
- 这一轮看到的那段提示词**原样**由「唤醒说明」决定（默认就是下面这段），
  插件不会把它改写成步骤：
  > 现在是空闲唤醒，没有人等回复。你可以什么都不做，也可以主动调用任意技能或发送想发的消息。多数时候什么都不做，有时只做一件事，很少同时做复数事情。没有想做的事就结束，不必发消息。
- **什么都不做时不发消息**：模型不调 `send_message` 就没有任何东西发出去，
  插件也不会补一句"我结束了"。控制台里会记一行"本轮未发消息"，这是**记录**，不是发言。
- **已经有人在等回复时跳过这次唤醒，且不算进当天次数**（有未读消息、或这一轮正在跑）。
- 只唤醒**白名单内的群**（与核心自己的主动循环同一套口径）。私聊不主动开轮。

## 它在哪一步做什么

| 时机 | 谁做的 | 做什么 |
|---|---|---|
| 每 30 秒 | 核心 `idleWakeTick()` | 问一句"有没有插件现在想开轮"（暂停中/没配模型/并发满了就不问） |
| 被问到 | 本插件 | 读设置 + 状态，判断时间段/间隔/当天次数/有没有人在等回复 → 返回要开的 chatKey |
| 收到 key | 核心 | `wake(chatKey, { proactive: true })` —— 开那一轮 |
| 这一轮跑起来 | 本插件 `before-context` | **确认开轮 → 这时才把当天次数 +1**，并认领这一轮 |
| 这一轮里 | 本插件 `before-llm-messages` | 把核心默认那句"主动抛个话题"**整段换成**唤醒说明（只动这一轮，正文一字不改） |
| 这一轮结束 | 本插件 `after-response` | 如实记下"发了 N 条 / 未发消息"，并交还这一轮 |

⚠️ **次数为什么等到"跑起来"才计**：核心在少数情况下会**静默丢弃**这次唤醒请求
（并发已满、机器人被禁言、模型未配置）。如果请求时就 +1，那几次会把当天额度白扣掉，
表现是"到点却不再醒"。所以计数挂在 `before-context`（核心开轮后跑的第一个钩子）上；
被丢弃的认领 10 分钟后自动过期，不会永久占着。

## 装了什么 / 放哪了

```
resources/app/plugins/continuous-life/
  plugin.json    清单（设置项、能力声明）
  index.js       实现
  README.md      本文件
```

状态存在 `data/continuous-life.json`（每个群的上次唤醒时间、当天次数、上次结果）。
删掉它只会让计时重置，不影响其它任何东西。

## 设置项（「插件」页 / 设置页的插件区）

| 设置 | 默认 | 说明 |
|---|---|---|
| 启用持续的生活 | **关** | 总开关。关着时插件完全不动：不询问、不开轮、不消耗 token。改完即时生效 |
| 开始时间（HH:MM） | 08:00 | 每天从这个时刻起才可能唤醒；支持跨零点 |
| 结束时间（HH:MM） | 20:00 | 过了这个时刻不再唤醒 |
| 最小间隔（分钟） | 120 | 两次唤醒至少隔这么久，最小 30 |
| 每天最多次数 | 5 | 每个群每天上限，范围 1–100，过 0 点重算 |
| 唤醒说明 | 见上面那段 | 这一轮实际看到的提示词，可改文字；只替换【未读信息】那一段，前面的记录/记忆/规则不动 |

## 自测

跑过两套（都在 Node 里直接驱动导出的纯函数，不需要起整个应用）：

**插件逻辑 42 项**：清单与目录归属、时间解析（`08:00`/`8:00`/`800`/跨零点/乱写回落）、
验收四项（关掉不唤醒 / 时段外不唤醒 / 间隔未到不唤醒 / 次数用完不唤醒）、
0 点重新计数、有人等回复时跳过且不计数、空闲无消息时能唤醒、多群各自独立计时、
记账与落盘、坏档自愈、提示词精确替换（含"找不到标记就不硬塞"）、
**请求开轮时不计数 / 开轮后才 +1 且同一轮只记一次 / 请求被丢弃时不白扣次数**、
"什么都不做"如实记账、职责边界（只导出能力与钩子，不注册工具、不拦工具）。

**核心桥集成 14 项**（真实 `plugin-loader` + 真实 `Orchestrator`，只换掉依赖与 `wake`）：
插件未生效时能力被过滤、核心一个都不问；生效时 `idleWakeTick()` 返回该群并调用
`wake(chatKey, { proactive: true })`；只扫白名单里的群不碰私聊；请求阶段不记账、
触发真实 `before-context` 后才 +1 且说明来自设置；间隔未到/次数用完/时段外都不开轮；
有人在等回复时跳过且不记账；核心的时序闸（节流、暂停、并发满、没有提供者时空转）；
以及"核心的 proactive 分支仍然允许无触发批"这条被本插件依赖的既有行为
（钉住它，将来核心若改动会先炸）。

## 排障

- **插件页显示"加载失败"**：把页面那句原因原样发出来（最常见是 `plugin.json` 少逗号）。
- **显示已启用，但到点没反应**：
  1. 先确认**核心改动已经生效**（重启过 QQ Agent）。没重启的话，插件再对，核心也不会问它 ——
     状态面板会显示「核心是否在询问：还没被问过」。
  2. 看状态面板的「未唤醒原因（抽样）」：会直接写出是哪一条闸拦住的
     （不在时间段 / 距上次唤醒多久 < 最小间隔 / 今天已唤醒几次达到上限 / 有人在等回复）。
  3. 空白名单时要确认 `allowAllWhenEmpty` 是开的，否则没有候选群。
- **开了轮但群里什么都没发生**：那是模型决定什么都不做，属于预期行为
  （状态面板的「上次结果」会写「未发消息（模型选择什么都不做）」）。
