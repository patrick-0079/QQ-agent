# 体力值（stamina）

给机器人加上一套「体力值」机制：说话、生图都要花体力，体力会随时间自己慢慢回，
不够了就在群里讨饭求群友投喂鱼饼。**每个群各算一份**，私聊里完全不生效。

---

## 一、它到底做了什么

| 行为 | 默认值 | 说明 |
| --- | --- | --- |
| 体力上限 | 60 | 投喂超出部分直接丢掉，不溢出、不存起来 |
| 每次发言 | −1 | 按「这一次要发几条」计费：一次发 3 条扣 3 点 |
| 每次生图 | −2 | 见下方【关于"生图"】 |
| 自然恢复 | 每 5 分钟 +1 | 关程序、重启、关机都不漏算 |
| 讨饭阈值 | < 10 | 低于 10 点开始在群里讨饭（乞求消息**不扣体力**） |
| 鱼饼 | 每人每天 2 个 | 每个 +15，@机器人说「投喂鱼饼」；**每天刷新、不叠加** |
| 主人 | 鱼饼无限 | 主人投喂不受额度限制 |
| 归零 | @主人求救 | 体力到 0 时 @ 主人 QQ 乞求投喂 |
| 查询 | @机器人说「查询体力」 | 回当前剩余体力 |

**各群独立**：A 群的体力跟 B 群毫无关系，一个群饿死了不影响别的群。
**私聊不生效**：私聊里不扣体力、不讨饭、也查不到体力（会明确告诉你没有这套机制）。

---

## 二、为什么是「插件」而不是「技能」

本项目的两种扩展只有一个判据 —— **谁决定何时执行**：

- `plugins/`（确定性型）：靠 providers / hooks，核心代码满足条件**必然执行**，模型绕不过去；
- `skills/`（LLM 型）：靠 registerTool，模型看着说明自己决定用不用。

「发言必须扣体力、体力不够必须发不出去」是**死规则** —— 模型想赖账也不该有机会。
所以计费与拦截走 hooks；而「有人 @ 我问体力」这种要理解人话的部分，也在
`before-context` 里被**确定性地**处理掉了（不经过 LLM，所以答数永远准）。
另外注册了一个只读的 `stamina__query` 工具，给「你还剩多少体力」这类**口语化**
提问兜底。

---

## 三、关于「生图」——请先读这一段

**本应用目前没有任何文生图 / 画图功能。** 我搜过整个 `src/`，不存在
`image_generate` / `draw_image` / `text2img` 之类的工具，也没有任何图片生成
的接口或 API Key 配置。

所以「每次生图扣 2 点」实际统计的是**发送网图**（内置工具 `send_image`）。
如果你以后装了真正的生图扩展（比如某个提供 `xxx__generate` 工具的插件），
只要把那个工具名填进设置里的**「算作『生图』的工具名」**，就会自动按生图计费，
不需要改代码。

## 四、设置项（全部可调）

控制台 → 技能 → 体力值。所有数值都能改，下面只列几个容易误解的：

| 设置项 | 默认 | 说明 |
| --- | --- | --- |
| 体力上限 | 60 | 调小时存量会跟着被夹下来，不会出现「24/20」 |
| 每次发言消耗 | 1 | 设为 **0** 等于发言免费 |
| 自然恢复间隔 | 5 分钟 | 与「每次恢复点数」共同决定速度 |
| 讨饭阈值 | 10 | 设为 **0** 等于彻底关掉讨饭 |
| 每人每天鱼饼数 | 2 | 按「群 + 人 + 当天」记账；跨天重置为满额（这就是「不叠加」） |
| 算作「发言」的工具名 | `send_message,send_to` | 用逗号分隔。**清空 = 发言不扣体力** |
| 算作「生图」的工具名 | `send_image` | 装上第三方生图后把它的工具名加进来 |
| 体力不足时拦下发言 | 开 | 关掉后体力只是个计数器，见底了照样能说话 |
| 主动讨饭 | 开 | 关掉就只在提示词里提醒它饿了，不主动出声 |
| 群里讨饭冷却 | 10 分钟 | 防刷屏 |
| @主人求救冷却 | 5 分钟 | |
| 讨饭检查间隔 | 60 秒 | 只影响反应快慢，不影响恢复速度 |
| 多久没人才不讨饭 | 30 分钟 | 只在这个时间内有人说过话的群才讨饭 |
| 主人 QQ 号 | 留空 | 留空 = 自动读「技能 → 主人识别」里配的主人 QQ（本应用的权威来源） |
| 投喂 / 查询指令关键词 | `投喂鱼饼…` / `查询体力…` | 想换触发词就改这里 |
| 各类文案 | 见设置页 | 支持 `{name}` `{stamina}` `{max}` `{gain}` 占位符 |
| 记录体力变动日志 | 开 | 每次扣费/投喂/恢复/拦截都往 `stamina.log` 写一行（排查全靠它，见第七节） |

## 五、安装

把 `stamina-plugin-v1.0.0.zip` 拖进控制台的扩展安装入口即可（会解到
`resources/app/plugins/stamina/`）。装好后到「技能」页确认它是启用状态。

数据落在 `<数据目录>/stamina.json`，一个文件装所有群，可以直接备份 / 迁移。

## 六、实现上几个刻意的选择

1. **恢复是懒计算的，不用定时器。**
   存一个「上次结算时刻」，下次读体力时按过了几个周期一次性补齐，余数留在锚点里。
   这样关机、重启、休眠都不漏算，也不会因为读取频繁而多算。

2. **计费放在 `after-tool`，不放在 `before-tool`。**
   `before-tool` 只**查**够不够（不够就否决），`after-tool` 在确认发送**成功**
   之后才真扣。否则「先扣钱再发现发送失败」就白扣了。两者顺序发生，所以
   「这轮只剩 1 点却想发两条」依然会被拦住。

3. **不擦改群友的消息。**
   `triggerEntries` 是浅拷贝数组，但**元素与核心存档是同一批对象**
   （`store.js` 的 `drainUnread` 直接返回 `st.messages` 里的条目，没克隆）。
   改 `m.text` 会把群友那条消息在内存存档里一起改坏。所以指令消息原样留给模型看，
   改用「本轮已由系统代答 → `before-tool` 否决它的发言工具」来保证不重复回一遍。

4. **讨饭消息不扣体力 —— 这是结构决定的，不是特判。**
   讨饭由插件自己发出，不经过 `before-tool`，所以天然免费。

5. **自己建一条只发不收的通道。**
   钩子的 context 里没有 `sender` / `onebot`，而核心的 `SendQueue` /
   `OneBotClient` 都建在 `createApp()` 闭包里、不导出单例，插件拿不到。
   本插件复用核心的 `SendQueue`（而不是裸调 `onebot.sendSegments`），这样
   Markdown 转纯文本、超长切分、CQ 转义、发送去重都还在。
   **但它不调 `connect()`** —— 不会开第二条 WebSocket、不会收到重复事件。

   两个已知代价（都是刻意选的）：
   - 本插件发出的回执**不进核心存档**，所以机器人下次看不到自己说过
     「当前体力 43/60」。这是因为 `ChatStore` 每会话在内存里缓存、`saveChat`
     整份覆盖写，第二个实例会把核心的聊天记录清掉 —— 宁可少一条记录，
     也不能清空聊天记录。
   - 它有自己的限频计数，与核心发言各算各的。

## 七、出问题了怎么查（先看这一节）

**这套机制的症状是"沉默的"**：插件没加载时它不会报错，只是什么都不扣、什么都不加，
看起来就像"数值坏了"。所以排查第一步永远是先确认它到底有没有加载。

**最省事的判据：看这两个文件在不在。**

```
<数据目录>\stamina.json     ← 状态（每个群剩多少）
<数据目录>\stamina.log      ← 变动流水（谁扣了、谁喂了、回了几点）
```

- **两个都不存在** → 插件从来没跑起来过。要么没重启，要么没加载。
  解决办法：完全退出 QQ Agent（注意托盘图标也要退），重新启动。插件目录是启动时
  扫描的，热重载虽然默认开着，但**新增**目录偶尔会漏，重启最稳。
- **`stamina.json` 存在** → 插件是活的，数值就在里面（`chats["group:群号"].stamina`）。
- **`stamina.log` 存在** → 里面每一行都是一次真实变动，例如：

```
2026-10-11T15:44:05.681Z -      ===== 插件已激活 v1.0.1（上限 60，每 5 分钟回 1 点，发言 -1，生图 -2，拦截=开）=====
2026-10-11T15:45:11.204Z group:1109764322 发言 2 条 -2 → 58/60
2026-10-11T15:46:02.881Z group:1109764322 2570893358 投喂 +15 → 60/60（今日 1/2）
2026-10-11T15:50:03.117Z group:1109764322 自然恢复 +1 → 59/60
```

  第一行的 `v1.0.1` 是**版本号**，`上限 60` 是**实际生效的上限** ——
  如果你把上限设成了 100 而这里显示 60，说明配置没读到，请把这一行发我。
  **"到底扣没扣"看这一行就够了，不用再猜。** 可以在设置里关掉（「记录体力变动日志」）。

**为什么插件要自己写一份日志？** 因为 `api.log` 走的是 `console.log`，而应用写进
`data\logs\qq-agent-*.log` 的是它自己的 logger —— **两者不是一条通道**。实测某台机器
的日志里一条 `[skill:xxx]` 都没有，也就是插件用 `api.log` 打的东西根本没落盘。
排查时这是致命的（什么都看不到），所以本插件直接往数据目录写 `stamina.log`。

**几个容易误判的点：**

- **"查询体力"回了个数字，但数值从来不变。**
  先看 `stamina.log` 有没有对应记录。**没有记录 = 那次根本没走插件**，那个数字是
  **模型自己编的** —— 它从提示词里知道"上限 60"，被问就顺口编一个。最容易踩的场景是
  **私聊**：私聊按设计完全没有体力机制，但模型仍会煞有介事地报一个数。
  （已在提示词里明确禁止编造数值；如果还遇到，把 `stamina.log` 发我。）
- **喂了没涨。** 体力**已满**时投喂不会涨（回执会说"已经吃饱了"，且**不消耗**对方当天
  额度）。想验证就先把 `stamina.json` 里的 `stamina` 改小，或者等它掉下来再喂。
- **说了话却没掉。** 自然恢复是每 5 分钟 1 点 = 每小时 12 点。如果你隔了二三十分钟
  才去查，之前的消耗早就被回满了，看起来就像"没扣"。`stamina.log` 里能同时看到
  `-2` 和后续的 `自然恢复 +N`，一眼就能分清。
- **喂了却涨不上去 / 到不了上限。** v1.0.0 有一个已修的 bug：读盘时把余额按**硬编码的
  默认上限 60** 夹了一遍（而不是你配置的上限），于是"投喂 → 79 存盘 → 读取夹回 60 →
  再投喂 → 80 → 又夹回 60"，永远卡在 60~80 之间，而且**不报任何错**。
  如果你把上限设成 100 却怎么喂都到不了，就是这个 bug —— 换 v1.0.1 即可。
  （v1.0.1 的 `stamina.log` 第一行会打印实际生效的上限，一眼可验。）
- **数据文件该在哪。** 跟着 `QQ_AGENT_DATA_DIR` 走（打包版 = exe 同级的 `data\`）。
  这样升级覆盖安装不会丢数据（安装程序只替换它自己装的文件，`data\` 不在清单里）。
- **装了但"技能"页里是灰的。** 看是不是被停用了，或者数据目录不可写
  （只读盘 / 权限不足）—— 后者会让插件自检失败并在控制台给出原因。

## 八、自测

```bash
cd resources/app/plugins/stamina
node selftest.mjs
```

`selftest.mjs` 会起一个假的 OneBot HTTP 服务收消息，把真实的
`src/sender.js` + `src/onebot.js` 串起来跑，覆盖 84 项断言：懒恢复的进位、
按条计费、失败不扣、体力不足拦截、各群独立、私聊不生效、鱼饼额度与跨天刷新、
主人无限、已吃饱不消耗额度、查询指令、只有 @ 机器人才触发、归零 @ 主人、
死群不讨饭，以及所有数值/名单设置项真的可调。

（该文件是开发期工具，默认**不会**被打进 zip —— 见 `make-zip.mjs` 的 `packSkill`。）
